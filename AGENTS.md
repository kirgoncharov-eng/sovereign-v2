# «Суверен» — правила студии

## Цель и границы

Играбельная коммерческая игра: жизнь правителя через людей с разными интересами.
Текст — ядро; у решения объяснимая цена; последствия живут дольше хода.
Первый срок должен хотеться доиграть и попробовать иначе. Выпуск и внешний тест — после явной приёмки Кирилла (#147).
Приоритет: поломки → `вкус-автора` → первая сессия и возвращение → качество существующего.
Новые механики до ворот A — только по решению Кирилла; идея оформляется задачей «Фича» с метрикой.

- Развиваем только Неманскую республику 1978 года (#115): независимость сохранилась после 1918-го.
  Реальные страны допустимы; политики, партии, персонажи и события вымышлены. Без комментариев к текущей политике.
- Шесть прежних стран — архив: новые партии закрыты, сохранения работают. Контент не развивать,
  кроме исправления поломки старого сохранения. Общий код не меняет архивные партии: сравнение с `main` и тесты совместимости.
- Антагонист интриги всегда мужчина и не посол. Новые строки проверять через `text-review` на разных зёрнах и сложностях 1978 года.
- Первая сессия до 10 минут, на ходу 1 без новых блоков. Ввод механик — `web/lib/game/desk-timing.ts`;
  после хода главная кнопка «Следующий ход». «Дело дня» одно на всех, результат проверяет сервер.
- Кирилл выбирает цели, принимает игру и мёржит. Не пушить в `main`. Мёрж не доказывает выкладку.

## Вход в задачу

- При начале сессии прочитать `STATUS.md` как указатель цели; проверить в GitHub свои замечания,
  входящие ревью и занятые файлы. При переходе к задаче обновить только относящиеся к ней сведения.
  Не перечитывать все PR, документы и репозиторий перед каждой правкой.
- GitHub — задачи и статус кода; Notion — решения, аудит и замеры; чат — обсуждение с Кириллом.
- До правок: проверяемые критерии в задаче, назначение на себя и `[studio:claim]` с агентом, веткой и файлами.
  Указывать фактические модель/effort, иначе «не подтверждены». Не покупать кредиты и не переходить на платный API автоматически.
- Один PR в активной разработке на исполнителя. После передачи на ревью разрешена непересекающаяся задача;
  исправления замечаний приоритетны. Не править файлы действующего автора и не включать чужие изменения.
- Читать затронутый код и его вызовы. Сначала восстановить недостающие факты, затем повышать effort.
  Базовые режимы: GPT-6.1 Sol / Medium, Sonnet 5.5 / Medium, Gemini 3.8 Flash / Medium.
  Более дорогой режим — под конкретный риск; смену не объявлять выполненной без подтверждения.
- GPT — реализация; Claude — сложные механики, редактура и глубокое ревью; Gemini — дизайн и арт.
  Это направления, а не запреты. Занятая задача сохраняет исполнителя до явной передачи.

## Правки, проверки и PR

- Одна задача — один PR и одна тема; промежуточные шаги — коммиты. `Closes #N` или `Part of #N`.
- Перед правками кода Next.js читать релевантные локальные docs по `web/AGENTS.md`, а не весь справочник.
- Читаемый код: содержательные имена, строки около 160 знаков, без минифицированного стиля.
  Новый модуль — с соседними `*.test.ts`. При изменении движка/контента «Дела дня» поднять `APP_VERSION`.
- Во время работы — проверки затронутого поведения. На готовом изменении кода — `cd web && npm run check && npm run build`.
  Для документов без кода — diff, ссылки и согласованность правил; локальная сборка игры не требуется.
  Проверку повторять после влияющих на неё правок, ошибок или новой неопределённости; результаты привязывать к SHA.
- Для игрового изменения автор проходит затронутый сценарий; для интерфейса — `playtest` и телефонные кадры ходов 1–3.
  Изменения общего движка требуют проверки совместимости архива и детерминизма.
- Перед мёржем — зелёный обязательный CI, актуальная база и отсутствие конфликтов. Проверки CI не отключать ради экономии.
- В PR: проблема и результат, класс, тип (**измерение / исправление ошибки / гипотеза роста**),
  критерии и фактические проверки, риски и зависимости. Для гипотезы — поведение игрока и ожидаемая метрика;
  для ошибки — нарушенное поведение; для процесса — устраняемые затраты, без обещаний роста игровых метрик.
- Итог хранится в PR; задача содержит ссылку. Не копировать отчёт в задачу, STATUS и Notion.
  Передачу незавершённой работы фиксировать один раз в задаче или PR, из другого места дать ссылку.
- `STATUS.md` — до 40 строк: цель, решения и важные блокеры со ссылками. Без ежедневного пересказа PR/CI.
  Обновлять при изменении цели, блокера или выпуска, отдельным статус-PR без других файлов (ограничение CI).

## Ревью по риску

| Класс | Изменения | Условие мёржа |
| --- | --- | --- |
| A | движок, сохранения, детерминизм, баланс, сюжетные ветки, состояние персонажей, данные игроков, юридические обязательства | независимое `approved` на актуальный полный SHA |
| B | текст без новых веток, интерфейс без новой логики, небольшие исправления | проверки автора; независимое ревью пакетом в ближайшем суточном окне |
| C | документы, правила, ассеты без кода, отчёты | проверки автора; независимое ревью и запрос на него не требуются |

Спорный случай — выше; проверяющий может повысить класс. Автор и соавтор не одобряют свой PR независимо.
Ревью игры проверяет и код, и опыт: действие понятно, цена видна, результат заметен.
Для A/B запрос и ответ — в PR, с подписью и полным SHA; новый head требует актуализации ревью.
Самопроверка, молчание и зелёный CI не заменяют независимого заключения.
