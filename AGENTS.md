# «Суверен» — правила студии

Этот файл читают все, кто работает над игрой: люди, Claude, GPT и другие агенты.
Здесь — куда мы идём, по каким правилам делаем изменения и кто за что отвечает.
Технические правила кода — в `web/AGENTS.md` (Next.js 16: перед кодом читать `web/node_modules/next/dist/docs/`).

## Куда идём

**Цель: играбельная коммерческая версия.** Сейчас — путь к мягкому запуску в русскоязычном Telegram и к проверке, возвращаются ли игроки.

Главные метрики (страница `/api/stats`, когорты по версиям):

| Метрика | Сейчас | Цель «ворот A» |
| --- | --- | --- |
| Дошли до финала первой сессии | 41% (14 игроков, до PR #18) | ≥ 50% |
| Вернулись на следующий день (D1) | 0% | ≥ 25% |
| Вернулись через неделю (D7) | нет данных | ≥ 8% |
| Поделились результатом | 0% | ≥ 5% |

Пока ворота A не пройдены на 300+ игроках, работа идёт в таком порядке:
1. Всё, что ломает игру или первую сессию.
2. Первая сессия и повод вернуться завтра.
3. Текст и логика уже существующих механик.
4. Новые механики — на паузе до ворот A. Идеи оформляем задачами «Фича» с метрикой; решение принимает Кирилл.

История аудитов и решений — в Notion, база «Аудиты» на странице «Суверен».

## Опоры игры

1. **Текст — ядро.** Каждая реплика логична: говорит тот, кого решение касается, место и время совпадают с делом, реакции идут от интересов людей. Без канцелярита и пустых слотов.
2. **У решения есть объяснимая цена.** Игрок видит, почему поручение силовикам стоит казне денег: разбивка по источникам, причины под вариантом.
3. **Первая сессия до 10 минут и без перегрузки.** На первых ходах — только дело, резолюция и газета. Новое (стол, программы, министры) появляется постепенно (`lib/game/desk-timing.ts`). Главная кнопка после хода — всегда «Следующий ход».
4. **Мир помнит.** Решения живут дольше одного хода: законы, обещания, интриги, программы.
5. **Соревнование — годы у власти.** «Дело дня» одно на всех, результат проверяется на сервере.

## Правила содержания

- Реальные страны — как модели. Реальных политиков, партий и фамилий в игре нет; люди, партии и события выдуманы.
- Никаких комментариев к текущей политике от имени игры.
- Тексты интриг написаны в мужском роде антагониста — антагонист всегда мужчина и не посол (есть тест).
- Каждая новая строка проверяется в партиях по всем шести странам (скилл `text-review`).

## Правила для каждого PR

- [ ] Одна задача GitHub, ссылка на неё в описании и проверка её критериев приёмки.
- [ ] Указаны тип изменения и метрика: **измерение / исправление ошибки / гипотеза роста**.
      Измерение делает метрику доступной, но само по себе не обещает её роста.
      Для гипотезы объяснить, какое поведение игрока изменится и почему ожидается эффект.
      Для ошибки описать нарушенное поведение. Без такого обоснования PR ждёт мягкого запуска.
- [ ] CI зелёный: `cd web && npm run check && npm run build`.
- [ ] Для изменений интерфейса — скриншоты ходов 1–3 на телефонном экране (скилл `playtest`, CI прикладывает их сам).
- [ ] Первая сессия не стала тяжелее: на ходу 1 нет новых блоков.
- [ ] Новый модуль — с тестами рядом (`*.test.ts`).
- [ ] Код читаемый: без однобуквенных имён и строк длиннее ~160 знаков. Сжатый «минифицированный» стиль не принимается.
- [ ] Один PR — одна тема. Большую фичу — частями, каждая играбельна.
- [ ] Поднята `APP_VERSION` в `web/lib/game/data.ts`, если меняется движок или контент «Дела дня».

| Кирилл (продюсер) | Цели, приоритеты, мёрж, решения по цифрам, живые тестеры |

| Claude | Ревью каждого PR, аудит, QA и плейтест, редактура текста, запуск и инфраструктура |

Задачи — на доске GitHub (Issues с метками и вехами). Кто берёт задачу — назначает себя, чтобы двое не правили одни и те же файлы.

## Приёмка задачи и координация

- До начала реализации у задачи есть проверяемые критерии приёмки и способ проверки каждого.
  Для аналитики явно указать единицу подсчёта, знаменатель, повторные события и исключение тестеров.
- Перед правками исполнитель назначает задачу на себя и пишет в ней список файлов.
  Если агенты используют один GitHub-аккаунт, в комментарии явно указать GPT/Codex или Claude.
- У исполнителя не больше одного PR в активной разработке.
  После передачи на ревью можно взять следующую задачу, если файлы не пересекаются.
  Пересекающиеся изменения ждут завершения предыдущей работы; исправления после ревью имеют приоритет.
- Работа идёт по вехе «Мягкий запуск», затем «Ворота A».

## Два уровня ревью

- **Код:** CI, корректность, сохранения, детерминизм, читаемость и критерии приёмки.
- **Опыт игрока:** понятно ли следующее действие, видна ли цена и заметен ли результат.
  Для изменений игры автор проходит затронутый сценарий до передачи PR;
  Claude независимо проверяет код и сценарий. В PR указать маршрут и наблюдения.
  Для документации или аналитики без изменения игрового пути допустимо «не применимо» с объяснением.
- Автоматический плейтест и прогоны агентов находят ошибки, но не доказывают интерес или удержание.
  Удержание проверяется на реальных игроках целевой аудитории.

## Определения метрик и замеры

- До нового замера Кирилл утверждает определения: событие, единицу подсчёта, знаменатель,
  окно наблюдения и исключения для финала первой сессии, D1, D7 и «поделились».
  Определения записываются в задаче замера или связанном аудите и не меняются внутри замера.
- В бессрочном правлении поражение, конец срока и завершение первого игрового захода — разные события.
  Точное определение «финала первой сессии» ещё требует утверждения; их нельзя смешивать в одной метрике.
- У каждого замера зафиксированы версия, источник трафика, даты и размер выборки.
  Разные версии и каналы показываются отдельно; неизвестный источник обозначается явно.
- Замер на 14 игроках до PR #18 — исторический. Его нельзя выдавать за результат текущей версии.
  Более быстрый проигрыш сам по себе не считается улучшением первой сессии.

## Ритм

- **Понедельник** — смотрим статистику, выбираем 3–5 задач недели под главную метрику.
- **Каждый PR** — ревью и CI до мёржа.
- **Пятница** — плейтест и аудит (скилл `audit`), запись в Notion, решение «что выпускаем».
- **Раз в неделю** — Кирилл выбирает согласованный набор проверенных изменений для выпуска.
  Фиксируем версию и состав выпуска; результат оцениваем по соответствующему замеру,
  не объединяя его автоматически со статистикой прежних версий.
